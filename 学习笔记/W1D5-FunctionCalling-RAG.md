# W1D5 Function Calling 与 RAG

## 对应仓库位置

- Function Calling: `11-integrating-with-function-calling`
- RAG: `15-rag-and-vector-databases`

## Function Calling 核心内容

Function Calling 的本质不是模型真的去执行函数，而是模型先输出一个结构化的“我要调用哪个函数、参数是什么”的决定，再由我们的程序去执行函数。

最重要的价值有三点：

1. 让输出更结构化，减少手写 JSON 解析和兜底逻辑。
2. 让模型可以借助外部能力，比如数据库、搜索接口、邮件、天气、库存。
3. 让应用控制权回到程序手里，模型负责决策，程序负责执行。

一个完整流程通常是：

1. 用户提问。
2. 把可用工具定义成 `tools/functions schema` 传给模型。
3. 模型判断是否需要调用工具。
4. 程序执行工具。
5. 把工具结果回填给模型。
6. 模型基于结果生成最终自然语言回答。

## Function Calling 注意点

1. `description` 和参数说明要写清楚，否则模型会猜错参数。
2. 不要把真正执行权限直接交给模型，程序必须做白名单校验。
3. 工具参数要做类型校验、缺失校验、范围校验。
4. 工具返回值尽量结构化，便于模型二次总结。
5. 工具太多会干扰选择，先给最必要的几个。

## RAG 核心内容

RAG 是先检索，再生成。

它不是让模型“凭记忆答题”，而是：

1. 把你的文档切块。
2. 给每个块生成 embedding。
3. 把 embedding 存到索引或向量库。
4. 用户提问时，把问题也变成 embedding。
5. 找最相关的几个块。
6. 把这些块和问题一起发给 LLM。
7. LLM 基于这些上下文生成回答。

RAG 的重点不是“让模型更聪明”，而是“让回答更基于你的数据”。

## RAG 注意点

1. Chunk 太大，召回不准；太小，上下文不够。
2. 检索到的上下文质量，直接决定最终回答质量。
3. 召回和生成是两段系统，不能只盯着最终答案。
4. 最好限制模型“仅根据提供上下文回答”，减少编造。
5. RAG 不等于微调。RAG 解决“接入最新/私有知识”，微调解决“行为风格和任务习惯”。

## 今天建议你抓住的区别

- Function Calling：让模型会“用工具”
- RAG：让模型会“读资料”

一句话理解：

- Function Calling 解决“去哪里拿能力”
- RAG 解决“去哪里拿知识”
